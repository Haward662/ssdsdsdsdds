# Памятка по интеграции API и типичным багам

В этом документе зафиксированы критические архитектурные особенности связки Frontend (React/Vite) + Backend (Node.js) + MongoDB + Telegram Bot, из-за которых возникали "плавающие" ошибки отображения контента.

## 1. Проблема: Бот обрезал длинные статьи
*   **Симптом:** При генерации статьи бот присылал только первые 2000 символов, хотя в базу данных статья сохранялась полностью.
*   **Причина:** Платформы типа VK Teams и Telegram имеют жесткие лимиты на длину одного сообщения (около 4096 символов). Изначально код (`backend/server.js`) брал только превью (`substring(0, 2000)`), чтобы гарантированно влезть в лимит.
*   **Решение:** Написан алгоритм "чанкования" (chunking). Бэкенд разбивает полный текст на куски по ~3800 символов, не разрывая строки (ориентируясь на символ переноса `\n`). Теперь бот отправляет статью серией сообщений ("Часть 1/N", "Часть 2/N") и только к последнему сообщению прикрепляет клавиатуру с кнопками "Одобрить / Отклонить".

## 2. Проблема: Фронтенд упорно показывал статичные статьи-заглушки
*   **Симптом:** Бот генерирует статьи, в логах PM2 статус "Опубликовано", база данных полна статей, но на сайте (`http://72.56.252.17:3001/#/blog`) всегда отображаются 6 старых статичных карточек.
*   **Причины:** Эта проблема состояла сразу из трех наслаивающихся архитектурных багов:

    ### Баг 2.1: Адреса API во время локальной разработки
    *   **Суть:** В проекте спрятан файл `.env.local`, который переопределял `VITE_ANALYTICS_URL` на `http://localhost:5000`. Так как сайт работал через Vite Dev Server (`npm run dev` на порту 3001), он отдавал код с зашитым `localhost`. Браузеры клиентов пытались найти API на своих домашних компьютерах, получали ошибку и... откатывались к отображению статики `articlesData`.
    *   **Фикс:** Файл `.env.local` был исправлен, URL жестко заменен на `http://72.56.252.17:5000`.

    ### Баг 2.2: Игнорирование API самим компонентом BlogPage
    *   **Суть:** В файле `App.tsx` корневой компонент успешно получал данные из API и складывал их в переменную `articles`. Но компонент `BlogPage` даже не ожидал эти данные как пропсы! Он напрямую импортировал жестко заданный массив из `articles-data.js` и рендерил его.
    *   **Фикс:** Компонент `<BlogPage />` переписан, чтобы принимать динамические данные: `const BlogPage = ({ articles, ... }) => { ... }`. В `App.tsx` прокинут пропс: `<BlogPage articles={articles} />`.

    ### Баг 2.3: Краш компонентов React из-за разницы ID
    *   **Суть:** Фронтенд ожидал, что у каждой статьи есть уникальное поле `id` (использовалось для `key={article.id}`). Однако MongoDB по умолчанию сохраняет идентификаторы в поле `_id`. Когда фронтенд мапил массив статей из БД, ключи оказывались `undefined`, что вызывало внутренние ошибки рендеринга и вынуждало UI возвращать статичные "резервные" данные. 
    *   **Фикс:** В эндпоинте бэкенда `/api/articles` (в `server.js`) добавлен промежуточный слой форматирования (mapping). Он берет результаты из Монго и форматирует их под идеальный стандарт, который ожидает React (переименовывает `_id` в `id`, подставляет картинки-заглушки для старых статей без картинок и автоматически вычисляет `readTime` и `excerpt`, если их нет).

## 3. Особенности работы на сервере
*   Вы запускаете сайт не через билд (Nginx -> `/dist`), а напрямую через встроенный сервер Vite (`npm run dev` на порту 3001). 
*   **Важное правило:** Из-за HMR (Hot Module Replacement) изменения в `.tsx` файлах фронтенд подхватывает на лету (иногда достаточно просто скопировать файл). Однако изменения в `.env` или логике бэкенда **обязательно** требуют ручного рестарта процессов на сервере (`pm2 restart all`).
